% SLIDE 1: What is CAN
% ==========================================
\begin{frame}{Controller Area Network (CAN) -- Key Attributes and Benefits}
	\begin{columns}[c]
		\begin{column}{0.60\textwidth}
			\fbox{\includegraphics[width=\textwidth,keepaspectratio]{\figures/can_bus.png}}\\
			{\small\textit{Two-node CAN bus and node composition}}
		\end{column}
		\begin{column}{0.40\textwidth}
			\begin{itemize}\setlength{\itemsep}{10pt}
				\item \textbf{Simple and low cost:} Single shared multi-master bus, widely used in automotive and industrial contexts
				\item \textbf{Robust:} Differential signaling, built-in error detection, faulty nodes isolated
				\item \textbf{Priority-based access:} Highest priority ID wins bit-wise arbitration
			\end{itemize}
		\end{column}
	\end{columns}
\end{frame}
\note{\footnotesize\begin{itemize}\setlength{\itemsep}{5pt}
		\item So --- what is CAN? It's a \textbf{serial bus} Bosch developed in the 1980s for ECUs in vehicles and industrial systems. The figure shows a two-node setup --- each node is a \textbf{CAN controller} plus a \textbf{transceiver IC}. Both share the same two wires, \textbf{CANH and CANL}, terminated at each end with \textbf{120\,$\Omega$} to kill reflections.
		\item \textbf{Simple and low cost:} Just \textbf{two wires}, shared by everyone. No master node --- any node can start a transfer.
		\item \textbf{Robust:} Differential signaling on CANH and CANL, so noise hits both wires equally and cancels out. Faulty nodes get isolated automatically through \textbf{bus-off}.
		\item \textbf{Priority-based access:} \textbf{Non-destructive} arbitration. The bus is a \textbf{wired-AND} --- dominant beats recessive. A losing node backs off the moment it sees a stronger signal.
	\end{itemize}}

% SLIDE: Bit Timing
% ==========================================
\begin{frame}{CAN Bit Timing and Synchronization}
	\fbox{\includegraphics[width=\textwidth,keepaspectratio]{\figures/bit_timing.png}}\\
	{\small\textit{CAN bit segmentation and sample point}}
	\begin{itemize}
		\item Receiving nodes do \textbf{hard synchronization} on the first frame bit and \textbf{resynchronization on recessive-to-dominant} edges mid-frame
	\end{itemize}
\end{frame}
\note{\footnotesize\begin{itemize}\setlength{\itemsep}{5pt}
		\item Each node runs on its own \textbf{independent oscillator} --- no shared clock. So there needs to be a mechanism to sync nodes and correct for drift during transmission.
		\item There are two sync types. \textbf{Hard sync} resets the bit timer on the first frame edge. \textbf{Resynchronization} corrects drift mid-frame by lengthening Phase\_Seg1 or shortening Phase\_Seg2 on a recessive-to-dominant edge.
		\item The figure shows two nodes: A leads, B is synchronized to A. Each bit splits into \textbf{Sync\_Seg}, \textbf{Prop\_Seg}, \textbf{Phase\_Seg1}, and \textbf{Phase\_Seg2} --- the \textbf{sample point} sits at the end of Phase\_Seg1. Prop\_Seg must cover the full \textbf{round-trip delay} so A has seen the settled bus level before sampling.
	\end{itemize}}

% SLIDE: Error Detection and Confinement
% ==========================================
\begin{frame}{Error Detection and Confinement}
	\begin{columns}[T]
		\begin{column}{0.60\textwidth}
			\textbf{Five error types}:
			\begin{itemize}\setlength{\itemsep}{3pt}
				\item \textbf{Bit:} transmitted bit $\neq$ monitored bus level
				\item \textbf{Stuff:} six consecutive identical bits detected
				\item \textbf{CRC:} computed vs.\ received remainder mismatch
				\item \textbf{Form:} fixed-form field violated
				\item \textbf{ACK:} no dominant ACK received
			\end{itemize}
			Any \textbf{detecting node sends an error flag} -- 6 dominant bits (error active) or 6 recessive bits (error passive)
		\end{column}
		\begin{column}{0.40\textwidth}
			\fbox{\includegraphics[width=\textwidth,keepaspectratio]{images/fce_simple.png}}\\
			{\small\textit{Fault confinement FSM}}
		\end{column}
	\end{columns}
\end{frame}
\note{\footnotesize\begin{itemize}\setlength{\itemsep}{5pt}
		\item This covers two things --- the \textbf{five error types} and how the node reacts when errors accumulate.
		\item Any detecting node immediately sends an \textbf{error flag}. An \textbf{error active} node sends 6 dominant bits --- that violates the stuff rule, forcing all other nodes to join in. An \textbf{error passive} node sends 6 recessive bits --- invisible to others, so the frame isn't destroyed.
		\item Each node independently tracks a \textbf{transmit error counter} (TEC) and \textbf{receive error counter} (REC). TEC goes up by 8 on TX errors, down by 1 on success. Three states: \textbf{error active}, \textbf{error passive}, and \textbf{bus off}.
		\item Once TEC exceeds 255 the node stops driving entirely. Recovery requires \textbf{128 sequences of 11 recessive bits} --- a deliberately long quiet period before re-joining.
	\end{itemize}}

% SLIDE: CAN vs CAN FD

\begin{frame}{CAN Classic (CC) vs. CAN Flexible Data Rate (CF)}
	\fbox{\includegraphics[width=\textwidth,keepaspectratio]{images/frame_format.png}}\\
	{\small\textit{CAN Classic and CAN FD frame structures}}
	\linebreak

	\footnotesize
	\begin{tabular}{p{0.30\textwidth} p{0.30\textwidth} p{0.30\textwidth}}
		\toprule
		Feature                      & CAN Classic                      & CAN FD                       \\
		\midrule
		Max bit rate                 & 1\,Mbit/s                        & 8\,Mbit/s (data phase)       \\
		Max payload                  & 8\,bytes                         & 64\,bytes                    \\
		Error detection HD$^\dagger$ & 6 typical, \textbf{2 worst case} & 6, all patterns, $\leq$64\,B \\
		Burst error detection        & up to 15\,bits                   & up to 17/21\,bits            \\
		\bottomrule
	\end{tabular}\\
	{\tiny $^\dagger$ CAN in Automation (CiA), \textit{CRC in CAN Frames}, can-cia.org.}
\end{frame}
\note{\footnotesize\begin{itemize}\setlength{\itemsep}{5pt}
		\item This compares the two frame formats the controller supports.
		\item The figure shows them side by side. CAN FD adds the \textbf{BRS bit} (bit rate switch), \textbf{ESI} (error state indicator), and a \textbf{longer CRC field} to support the higher data rate and bigger payload.
		\item \textbf{Max bit rate / payload:} CAN Classic tops out at \textbf{1\,Mbit/s} and \textbf{8 bytes}. CAN FD switches to up to \textbf{8\,Mbit/s} in the data phase and supports \textbf{64 bytes}.
		\item \textbf{Error detection HD:} In CAN Classic, two errors can relocate a stuff bit so the corrupted frame produces the same CRC remainder --- that's \textbf{HD=2}. CAN FD feeds stuff bits into the CRC and adds the \textbf{SBC field}, so any relocation changes the remainder --- \textbf{HD=6} restored.
		\item \textbf{Burst error detection:} CRC-15 catches all \textbf{15-bit bursts} for free. CAN FD uses \textbf{CRC-17/21} to raise the ceiling and maintain HD=6 over 64-byte payloads.
	\end{itemize}}

				\item State transition on the sample point strobe from \texttt{can\_pcs}.
				\item Valid received frames are streamed to the LLC by a separate Avalon-ST interface control process, \texttt{p\_stream}.
			\end{itemize}
		\end{column}
		\begin{column}{0.40\textwidth}
			\begin{center}
				\includegraphics[,height=0.85\textheight,keepaspectratio]{images/fsm.png}
			\end{center}
		\end{column}
	\end{columns}
\end{frame}
\note{\footnotesize\begin{itemize}\setlength{\itemsep}{5pt}
		\item \texttt{can\_mac\_fsm} is the \textbf{central orchestrator} of the MAC layer --- by far the largest module. Three helper modules handle bit stuffing, CRC, and TX serialization.
		\item \textbf{State graph:} CAN Classic and CAN FD are identical up to the FDF bit --- then the field sequences diverge. BRS, ESI, longer data, SBC, different CRC. One \textbf{FSM state per frame field} --- makes the FSM directly readable against the frame structure.
		\item \textbf{\texttt{is\_transmitter}:} The FSM handles both TX and RX in a single state graph. The flag gates which logic runs in each state --- no separate TX and RX FSMs.
		\item The FSM advances on the \textbf{sample point strobe} from \texttt{can\_pcs}. The next bit is driven two clock cycles later, once \texttt{can\_mac\_bs} and \texttt{can\_mac\_crc} outputs have settled.
		\item Valid received frames are streamed to LLC via a separate \textbf{Avalon-ST} process.
	\end{itemize}}

% SLIDE MAC-2: Bit stuffing

\begin{frame}{MAC: \texttt{can\_mac\_bs} -- Bit Stuffing and Destuffing}
	\begin{columns}[c]
		\begin{column}{0.50\textwidth}
			\textbf{Dynamic stuffing} (CC and CF):
			\begin{itemize}\setlength{\itemsep}{6pt}
				\item Transmitter inserts inverse bit after five consecutive identical bits
				\item Receiver strips stuff bits and checks for violations
			\end{itemize}
			\vspace{0.4em}
			\textbf{Fixed stuffing} (CF CRC region only):
			\begin{itemize}\setlength{\itemsep}{6pt}
				\item Stuff bit at fixed intervals
				\item SBC: Gray-coded dynamic stuff count + parity
			\end{itemize}
		\end{column}
		\begin{column}{0.50\textwidth}
			\begin{center}
				\includegraphics[width=1.0\textwidth,keepaspectratio]{images/bs.png}
			\end{center}
		\end{column}
	\end{columns}
\end{frame}
\note{\footnotesize\begin{itemize}\setlength{\itemsep}{5pt}
		\item This shows \texttt{can\_mac\_bs} and its interface with \texttt{can\_mac\_fsm}. Valid/data interface in both directions --- enable selects dynamic vs.\ fixed stuffing.
		\item \textbf{Dynamic stuffing:} After five consecutive identical bits the transmitter inserts the inverse bit. Receiver strips it and flags a stuff error if it's missing. Applies from SOF through the data field in both CC and CF.
		\item \textbf{Fixed stuffing:} In the CF CRC region, stuff bits go in at \textbf{fixed intervals} --- not data-driven.
		\item \textbf{SBC:} \textbf{Gray-coded} count of dynamic stuff bits inserted since SOF, plus a parity bit. Transmitted just before the CF CRC. This is what fixes the HD=2 problem --- any relocation of a dynamic stuff bit changes the SBC and the CRC remainder.
	\end{itemize}}

		\end{column}
		\begin{column}{0.50\textwidth}

\end{frame}
\note{\footnotesize\begin{itemize}\setlength{\itemsep}{5pt}
		\item This is \texttt{can\_mac\_crc} and its interface with \texttt{can\_mac\_fsm}. \textbf{Three CRC engines running in parallel} --- one per generator polynomial. Dual data feed from the FSM, one stream per format.
		\item \textbf{Three parallel engines:} CRC-15 for CC, CRC-17 for short CF payloads ($\leq$16\,bytes), CRC-21 for longer ones. Running in parallel avoids any timing dependency on knowing the format early.

% SLIDE MAC-5: FCE
% ==========================================
\begin{frame}{FCE: \texttt{can\_fce} -- Fault Confinement Entity}
	\begin{itemize}\setlength{\itemsep}{10pt}
		\item The error counting FSM has three states: error active, error passive, bus off -- driven by TEC and REC thresholds.
		\item The module subscribes to error events from \texttt{can\_mac\_fsm}. It signals \texttt{error\_active} and \texttt{bus\_off} back according to the thresholds of the error counting FSM.
		\item An active bus-off signal is lowered after 128 \texttt{idle\_condition} strobes from \texttt{can\_pcs}
	\end{itemize}
\end{frame}
\note{\footnotesize\begin{itemize}\setlength{\itemsep}{5pt}
		\item The FCE sits \textbf{outside the data path} and monitors TX and RX error events. It maintains error counters and updates the node error state accordingly.
		\item \textbf{Three states:} TEC and REC --- up by 8 on errors, down by 1 on success. Above 127 the node enters \textbf{error passive} --- its error flags are recessive and invisible to other nodes. Above 255 it goes \textbf{bus off} and stops driving entirely.
		\item Two special error events: \textbf{passive\_tx\_ack\_error} is exempt from TEC increment --- ISO rule, to avoid stranding an error-passive transmitter at bus off. \textbf{error\_delim\_too\_late} is a stuck-dominant fault and hits both counters by 8.
		\item \textbf{Bus-off recovery:} ISO mandates \textbf{128 sequences of 11 recessive bits} before re-joining. The \texttt{idle\_condition} strobe from \texttt{can\_pcs} counts these.
	\end{itemize}}

% ==========================================
% SLIDE: TDC concept
% ==========================================
\begin{frame}{Transmitter Delay Compensation (TDC)}
	\begin{center}
		\includegraphics[width=\textwidth,keepaspectratio]{\figures/tdc.png}
	\end{center}
	\begin{itemize}
		\item At high data rates the \textbf{transceiver loop delay} can exceed the bit time -- TX echo arrives too late for the normal SP
		\item Without compensation \textbf{bit-error monitoring} fails in the data phase
		\item TDC measures the delay on the \textbf{reserved bit} and defers the \textbf{SSP} to match
	\end{itemize}
\end{frame}
\note{\footnotesize\begin{itemize}\setlength{\itemsep}{5pt}
		\item Before the PCS slide --- a quick detour to explain \textbf{TDC}. It's the key concept driving the added complexity in CAN FD bit timing.
		\item The problem: the transmitter detects bit errors by monitoring its own \textbf{echo on the bus}. At high data rates the \textbf{transceiver loop delay} can exceed the bit period --- the echo arrives too late. The transmitter reads the previous bit instead of the one it just drove. Bit errors go undetected.
		\item The figure shows TX driving bits and the delayed RX echo. In the early data-phase bits the SP fires at the wrong position --- marked \textbf{Invalid SSP} --- because the echo hasn't arrived yet. Once the TDC offset is known the SSP fires correctly.
		\item \textbf{TDC measurement:} The transmitter drives the FDF bit and starts a counter. It watches for the RX echo of the \textbf{reserved bit}. The counter value when the echo arrives is the \textbf{transmitter delay} --- applied to every subsequent SSP in the data phase.
	\end{itemize}}

\begin{frame}{PCS: \texttt{can\_pcs} -- Bit Timing and Transmitter Delay Compensation (TDC)}
	\begin{columns}[c]
		\begin{column}{0.50\textwidth}
			\begin{itemize}\setlength{\itemsep}{6pt}
				\item SP strobes at end of PHASE\_SEG1
				\item Transmit bit on TX line at end of PHASE\_SEG2
				\item SSP strobe used for bit-error monitoring in data phase
				\item Switch to data phase bit rate at BRS bit
				\item Transceiver loop delay measured on res bit
			\end{itemize}
		\end{column}

\section{Conclusion}
\begin{frame}{Conclusion and Future Work}
	\small
	\begin{columns}[T]
		\begin{column}{0.48\textwidth}
			\textbf{Conclusions}
			\begin{enumerate}\setlength{\itemsep}{3pt}
				\item Full TX/RX for all four frame formats -- 28/37 requirements closed, 4,608\,LE at 127\,MHz
				\item ISO layered model is a practical design partitioning -- each sub-layer independently implementable and testable
				\item BRAM migration is the primary LE reduction path --- eliminates write-enable decode and read mux
			\end{enumerate}
		\end{column}
		\begin{column}{0.48\textwidth}
			\textbf{Future work}
			\begin{enumerate}\setlength{\itemsep}{3pt}
				\item \texttt{can\_llc} implementation
				\item Hardware bring-up with a re
				\item BRAM migration for RX frame buffer
				\item REQ-021 frame-aware error injection
				      (all four error types)
			\end{enumerate}
		\end{column}
	\end{columns}
\end{frame}
\note{\footnotesize\begin{itemize}
		\item So to close -- here are the three main conclusions and where the work goes next.
		\item \textbf{Full TX and RX} for all four frame formats in VHDL-93. \textbf{28 of 37 requirements} closed --- all P1 requirements across MAC, PCS, and FCE verified. \textbf{4,608 LEs} at \textbf{127\,MHz}.
		\item The \textbf{ISO layered model proved a practical partitioning} --- each sub-layer was implemented, verified, and debugged independently. That's exactly the property that makes in-house development viable for Everllence --- they own and can maintain every layer.
		\item \textbf{BRAM migration} is the primary LE reduction path. With flip-flop registers each of the 512 payload FFs needs its own \textbf{individual write-enable} --- that's the 2,048 LE cost. With BRAM you compute one shared \textbf{write address} instead, and the RAM handles internal selection. The 560 storage FFs and 552 LE read mux are also eliminated. Net saving: ~2,600 LEs, leaving \texttt{can\_mac\_fsm} at protocol-logic cost.
		\item Future work: \texttt{can\_llc} is the next layer up. \textbf{Hardware bring-up} with a reference PCAN node validates the physical layer end-to-end. \textbf{BRAM migration} cuts the LE count as discussed. \textbf{REQ-021} needs frame-aware error injection to close the remaining sub-claims.
	\end{itemize}}
