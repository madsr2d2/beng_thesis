# Requirements Engineering & Initial Design Strategy

## Motivation: Taming a Disorganized Specification

A foundational challenge in any formal verification effort is establishing a clear, traceable link between the specification and the verification environment. In the context of this project, the authoritative source of truth is the ISO 11898-1 standard, which defines the CAN and CAN FD protocol at the data link layer. However, the standard is not structured with verification traceability in mind. Normative requirements are scattered across numerous subsections, often repeated or paraphrased from different perspectives, and interspersed with descriptive and explanatory text. This makes it difficult to identify, enumerate, and systematically link individual requirements to specific testbench components and checkers. Without a structured requirements artifact, the risk is that verification coverage becomes informal and anecdotal — a situation that is particularly problematic in a safety-relevant protocol context such as CAN.

To address this, the aim was to condense the ISO 11898-1 specification into an easily referenceable requirements table, where each entry carried a unique label that could be explicitly referenced from testbenches and checkers in the verification environment. This would establish a formal traceability chain from specification to verification, making it possible to argue with confidence about the completeness of the verification effort.

---

## AI-Assisted Requirements Extraction

Producing such a table manually from scratch would have been an extremely labor-intensive undertaking. Instead, an AI-assisted requirements extraction pipeline was developed. The ISO standard was first converted into Markdown format, making it easily searchable and ingestible by a Claude Sonnet 4.6 language model agent. The agent was then prompted to extract all normative language from the document — including sentences containing "shall", "shall not", "should", and "should not", the canonical markers of mandatory requirements and recommendations respectively in ISO standards. Each extracted statement was classified according to the subsection of the standard it appeared under, with initial classification labels corresponding directly to the ISO layer structure: the MAC layer, the LLC layer, the fault confinement logic, and the PCS layer.

It is worth noting that the extraction prompt was intentionally broad in its scope of normative language. Rather than filtering strictly on mandatory "shall" and "shall not" statements, the prompt also captured "should" and "should not" statements — the ISO standard's markers for recommendations rather than hard requirements. This decision was deliberate: while "should" statements are technically optional from a conformance perspective, they represent best-practice behaviors that a robust CAN FD implementation ought to exhibit, and excluding them entirely risked producing a requirements table that was conformance-complete but implementation-incomplete. The distinction between mandatory and recommended requirements was preserved as metadata in the table, allowing the verification effort to prioritize accordingly while retaining full visibility of the recommendation landscape.

This initial extraction yielded 168 normative statements. While this represented a comprehensive first pass, the raw output had significant limitations. Many of the extracted statements were effectively descriptions of the same underlying requirement, expressed from slightly different angles or in different parts of the document — a direct reflection of the standard's disorganized structure. In this sense, the extraction process faithfully mirrored the disorganization of the source document, which was itself a useful diagnostic: it made the scale of the consolidation problem immediately visible.

---

## Manual Condensation: The Expensive Part

The process of condensing the 168 raw extractions into an organized, non-redundant requirements table was largely manual and time-consuming. It required repeated close reading of the relevant standard sections, identifying which statements described the same underlying behavior, and paraphrasing the often verbose normative language into precise, concise requirement statements. This kind of semantic consolidation — distinguishing between a restatement and a genuinely distinct requirement — is not a task that can be fully automated, as it requires domain-level understanding of the protocol. The LLM agent did not assist substantially in this condensation phase.

The scale of the consolidation effort is perhaps best conveyed by the numbers: 168 raw normative extractions were condensed into a final table of 48 requirements — a reduction to roughly 29% of the original count. This means that on average, each final requirement entry absorbed and unified roughly three to four raw extractions, each of which had described the same underlying behavior from a different angle or in a different part of the document. This degree of redundancy in the source material is itself a telling commentary on the structure of the ISO standard, and underscores why an unprocessed extraction could not have served as a usable verification reference.

Nevertheless, the LLM agent unquestionably earned its keep by bootstrapping the initial content of the verification plan data structure. Starting from a blank requirements table would have been a significantly more daunting undertaking; having a populated, classified starting point — even one requiring substantial revision — dramatically reduced the upfront effort and gave the manual review process a concrete artifact to work from and react to. This is an underappreciated mode of LLM utility in engineering workflows: not autonomous completion of a task, but the generation of a rough first draft that makes the subsequent human effort more tractable.

It is also worth noting that the requirements table was not a document that froze at a single point in time. Rather, it functioned as a living document throughout the project, evolving as implementation and verification work revealed aspects of the specification that had been misunderstood, overlooked, or insufficiently specified in the initial extraction. This iterative refinement is arguably an inherent property of requirements engineering in complex protocol implementations, and should be expected rather than treated as a sign of process failure.

## Enriching the Requirements Structure

Through further manual review and additional LLM-assisted iterations, the requirements data structure was enriched with several dimensions beyond the raw normative text:

- **Layer** (MAC, LLC, fault confinement, PCS, or system): indicating which architectural layer the requirement pertained to. A fifth label — "system" — was introduced alongside the four protocol layers to classify requirements that were inherently multi-layer or multi-node in character. Some CAN behaviors cannot be attributed to a single layer of a single node; they emerge from interactions between multiple nodes on the bus, or span the layer boundary within a single node. Attempting to force such requirements into a single-layer classification would have been misleading and would have obscured their true verification implications. The system label acknowledged this explicitly, flagging these requirements as ones that could not be fully verified through isolated unit testing of individual modules, but would instead require either an integrated multi-module testbench or a multi-node simulation environment.

- **Side** (TX or RX): indicating whether the requirement applied to the transmitter path, the receiver path, or both.

- **Observability** (black-box or white-box): classifying whether the requirement could be verified purely from the observable inputs and outputs of the relevant layer, or whether it referenced internal states and therefore necessitated some form of reference model in the verification environment. A black-box requirement depends only on the observable inputs and outputs of the layer to which it pertains and can therefore be verified without knowledge of internal implementation state. A white-box requirement references internal states or variables of the layer and generally necessitates a reference model running in parallel with the design under test, or formal PSL assertions that directly reference internal signals.

- **Verification method** (coverage, simulation, waveform inspection, or code inspection): indicating the primary verification technique applicable to each requirement. Coverage requirements involved checking that a range of values or behaviors had been exercised — for instance, that the CAN module was capable of transmitting frames across the full range of valid payload lengths. Such requirements mapped naturally onto OSVVM coverage models and coverage-directed randomization strategies. Simulation requirements were verified through explicit stimulus/response testing in a testbench, with automated checkers asserting expected outputs. Waveform inspection requirements — typically white-box requirements where automated checking was impractical — required manual inspection of simulation waveforms generated by a testbench run. Code inspection requirements were verified by reading and reasoning about the RTL source directly, without simulation.

The observability and verification method dimensions in particular had direct downstream consequences for the verification strategy. Black-box requirements could in principle be verified purely through stimulus-response testing, while white-box requirements pointed toward the need for either a behavioral reference model or formal PSL assertions checking internal state. The verification method dimension made this mapping explicit and actionable, giving each requirement a clear path to verification from the outset.

The requirements table was maintained in a human-readable, version-control-friendly format — specifically a structured text format amenable to diffing and change tracking — allowing it to be rendered as a navigable reference document and cross-referenced from testbench comments and assertion labels. This gave the verification environment a concrete anchor point for traceability arguments.

## Traceability: Linking Requirements to Testbenches

Each requirement entry in the table carried two dedicated traceability fields: a **file** field and a **label** field. The file field identified the specific testbench file responsible for covering that requirement. The label field identified a specific named procedure within that testbench that implemented the checker or stimulus for the requirement in question. This established a direct, navigable link from each requirement to its verification artifact, making it possible to assess coverage status by inspection rather than inference.

For requirements verified by waveform inspection, only the file field was populated — since there was no automated checker procedure to reference, only a testbench whose output waveforms required manual interpretation. For code inspection requirements, the file field pointed to the relevant RTL source file rather than a testbench. This consistent field structure across all verification methods meant that the traceability mechanism was uniform regardless of the technique used, and that gaps in coverage — requirements with unpopulated traceability fields — were immediately visible.

## A Red Herring in the Requirements Structure

In retrospect, the TX/RX side dimension introduced a subtle but consequential bias into the early design thinking. Organizing requirements along the transmitter/receiver axis made intuitive sense from a specification perspective — the ISO standard itself frames many requirements in terms of transmitter behavior and receiver behavior — and it was genuinely useful for thinking through which requirements belonged where. However, it also made a split-path implementation architecture look like the natural and obvious design strategy, simply because the requirements were literally organized along that split. The implication seemed to be: implement a TX module, implement an RX module, map the TX requirements to the former and the RX requirements to the latter.

This turned out to be something of a red herring. The pitfalls of the split-path approach — the design drift, the integration complexity, the duplicated hardware — were not at all apparent from the requirements table alone. On the contrary, the table made the split architecture look clean and well-motivated. The problems only surfaced later, during integration. This is an important general lesson: the structure of a requirements model can inadvertently bias architectural decisions in ways that are not immediately obvious, and the apparent naturalness of a design strategy that mirrors the requirements structure is not in itself a reliable signal that the strategy is sound.

## Limitations of the Requirements Table Approach

An intellectually honest account of the requirements engineering process should acknowledge what the requirements table could not fully capture. Several categories of limitation were encountered.

First, the flat tabular format struggles to express temporal and ordering relationships between requirements. Many CAN behaviors are inherently sequential — a transmitter error flag must be followed by an error delimiter, which must be followed by a specific interframe spacing — and while individual steps in such sequences can be captured as separate requirements, the ordering constraints between them are difficult to express compactly in a table row. These relationships were partially addressed through natural language descriptions in the requirement entries, but a more expressive formalism — such as temporal logic or a state-transition specification — would have been better suited to capturing them precisely.

Second, requirements describing bus-level interactions between multiple nodes present a fundamental verification scope challenge. Such requirements, labeled with the system layer classification, cannot be fully verified through single-node unit testing. They require either a multi-node simulation environment or a formal argument about the emergent bus behavior from the individual node specifications. This represents a genuine gap in what the unit testing strategy can achieve, and is worth acknowledging explicitly rather than implicitly.

Third, the ISO standard occasionally employs language that resists unambiguous reduction to a single testable requirement statement. Some normative sentences contain implicit assumptions about system context that are not fully specified, or use terms that are defined elsewhere in the standard in ways that are themselves open to interpretation. In such cases, the requirements table entry necessarily embeds a design decision about how the ambiguity was resolved — a decision that ideally should be documented and justified rather than silently made.

These limitations do not undermine the value of the requirements table as a verification planning tool, but they do define the boundary conditions of its utility and point toward areas where complementary specification and verification techniques are needed.

## The Existing In-House CAN Module as a Reference Point

An important resource throughout the design process was the existence of an in-house Classical CAN implementation, developed prior to this project, which served as both an architectural reference and a source of design inspiration. The availability of a known-good CAN implementation meant that the project was not starting entirely from first principles; the existing module provided a concrete reference point for what a correct CAN implementation looked like at the RTL level, and informed many of the structural decisions made in the CAN FD extension.

The existing module's MAC layer was implemented as a single unified FSM — a design decision that, in retrospect, validated the eventual conclusion reached independently in this project after the failed split-path experiment. However, the existing implementation differed from the architecture settled upon here in one important respect: it did not give fault confinement its own dedicated entity. Instead, fault confinement logic was implemented as a separate process within the same file as the MAC FSM, effectively co-locating the two in a single compilation unit. While this is a reasonable design choice — fault confinement is closely coupled to MAC layer error detection — it conflates two conceptually distinct responsibilities, which complicates both independent unit testing and requirements traceability at the fault confinement layer level.

In this project, the decision was made to give fault confinement its own dedicated entity, aligned with the layered requirements classification scheme. This separation was motivated precisely by the requirements engineering work: since fault confinement requirements had been extracted and labeled as a distinct layer, it was natural and desirable to have a corresponding dedicated module against which those requirements could be unit-tested in isolation. The existing in-house implementation thus served as a useful baseline to reason against — informing the design not just through the decisions it had made, but also through the design choices it suggested could be reconsidered.

---

## Architectural Alignment with the ISO Layer Model

Despite the eventual complications introduced by the TX/RX split, the broader decision to align the module architecture with the ISO standard's layered framing proved sound. A dedicated hardware module was created for each layer — MAC, LLC, fault confinement, and PCS — and within each module, both a TX path and an RX path were initially implemented as distinct internal structures.

This modular architecture offered a significant verification advantage: requirements pertaining to a given layer could be verified in isolation against that layer's module, rather than having to be observed through the surface of a fully integrated system where internal behavior would be obscured by the surrounding logic. The layer dimension of the requirements table mapped cleanly onto the module hierarchy, and the observability dimension mapped cleanly onto the choice of verification technique for each module. This made it straightforward to construct a structured, requirements-driven unit testing strategy, where each testbench could be explicitly linked to the subset of requirements it was designed to exercise.

## MAC Layer FSM: From Split Paths to Unified Design

The bulk of the control logic resides in the MAC layer, which hosts the main finite state machine (FSM) responsible for frame generation and reception. In line with the initial TX/RX split architecture — reinforced, as noted above, by the structure of the requirements table — the MAC layer FSM was initially developed as two separate state machines, one governing the TX path and one governing the RX path, each with its own testbench.

Several problems emerged as the split-path design was developed and subsequently integrated. The first was a practical consequence of temporal separation: the two FSMs were implemented at different points in time, and even though the underlying logic was fundamentally the same, this caused design decisions to drift and diverge unnecessarily. Subtle inconsistencies accumulated between the TX and RX FSMs — not because the requirements differed, but simply because different implementation choices were made in the moment. When it came to integrating the two paths, these accumulated divergences made debugging significantly more complicated than it needed to be, as it was difficult to retrospectively identify where and why the two designs had deviated from each other. This is a well-known pitfall in RTL design: when two structurally similar modules are developed in sequence by the same designer, they tend to accumulate inconsistencies that violate the implicit assumption that they are implementing the same logic. The general lesson is a "single source of truth" principle: if two modules are structurally identical, they should be the same module, parameterized or role-flagged, rather than two separately maintained copies.

The second problem was more fundamental. A complete CAN node inherently assumes both the transmitter and receiver roles: at different points on the bus a node may be actively transmitting or passively receiving, and even within a single frame a transmitting node must simultaneously monitor the bus as a receiver — most notably during the acknowledgment phase, where it must detect whether any other node has pulled the ACK slot dominant. This inherent duality means the TX and RX paths are not truly independent; their behavior is tightly coupled by the protocol, and treating them as fully separate modules introduced artificial complexity at the integration boundary.

Furthermore, a structural observation made the split architecture redundant at the FSM level: the state sequences for the TX and RX paths are essentially identical, since both must process the same CAN frame structure in sequence. The divergence between the two roles is not in the state space but in the actions taken within certain states — whether the node is driving the bus or sampling it. Maintaining two separate FSMs to represent this distinction was unnecessary.

For all of these reasons, the TX and RX FSM designs were merged into a single unified FSM, with a role flag distinguishing transmitter behavior from receiver behavior within shared states. This consolidation offered several concrete advantages. First, it eliminated design drift by construction: with a single FSM, any change to the shared logic automatically applies to both roles, and there is no risk of the two paths diverging again in future development. Second, it substantially improved debuggability: with a unified state space, debugging the integrated system required inspecting only a single file and tracking a single current state, rather than cross-referencing two separate FSMs with subtly inconsistent design histories. Third, it yielded a meaningful reduction in hardware area. The MAC layer contains several submodules beyond the FSM itself — notably a CRC module for computing cyclic redundancy checks on frames, and a bit stuffing module for handling bit stuffing during frame transmission and reception. In a split-path architecture, each path would require its own dedicated instance of these submodules. By unifying the FSM, both the transmitter and receiver roles can share the same physical CRC and bit stuffing hardware, time-multiplexing access to it depending on which role the node is playing at any given moment. This resource sharing represents a non-trivial area saving in the final implementation.

The unification of the MAC layer FSM thus resolved the main architectural complication introduced by the initial split-path strategy, and set a cleaner foundation for the subsequent implementation and verification work described in the following sections.
